fix: string options whose value is used as a header name or written into a header are checked when the interceptor is created, naming the option, instead of failing each request as an internal error. `createGatewayAuthInterceptor` throws for a header name in `headerMapping`, `trustSource.header` or `stripHeaders` that is not a valid HTTP header name, and, with `propagateHeaders` on, for a `defaultType` that is empty, longer than 128 characters or holds a lone surrogate (with `propagateHeaders` off the value is accepted as before). `meshIdentityTrust`, `signedTokenTrust` and `sharedSecretTrust` throw for an invalid `header` name. `createClientGatewayInterceptor` throws for an empty `secret`, a `secret` with a line break, a character above U+00FF or a space or tab at either end (the platform removes that whitespace, so the secret never matched), an empty `subject` or one with a line break or a lone surrogate, and `roles` that is not an array of strings without holes that fits the roles header. `setAuthHeaders` refuses an empty subject or type, which the reader reads as absent. A configuration that relied on one of these values must change it.
