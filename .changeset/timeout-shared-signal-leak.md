fix: `createTimeoutInterceptor` no longer retains about 8 KB per call when many calls share one long-lived `AbortSignal` (an application-wide shutdown signal, for example). The leak showed on Node with `server.localClient()` calls and was never freed by garbage collection: after 6000 calls the heap had grown by about 50 MB, and it now grows by under 1 MB. A unary call gets a per-call signal that follows the caller's abort only while the call runs, and the caller's abort reaches downstream work with the caller's own reason as before. While the handler is still running, the caller's abort reaches it as before. One consequence: an abort of the caller's signal that arrives only after the call has already returned (over HTTP, a signal-unaware handler can finish before the server learns of the cancellation; measured on the previous release, the handler's signal was not aborted at the moment it returned and was aborted later only through the lingering link) no longer flips the signal that finished call's handler held. Streaming calls (opt-in with `skipStreaming: false`) keep following the caller's signal for the life of the stream, so a shared signal still accumulates one link per such stream until it aborts.
