feat: a method can require an action on a specific object named by the request, declared in the proto contract. `MethodAuth` gains a repeated `resources` field; each `ResourceRequirement` gives an `action`, the request field that holds the resource id (`id_field`, a dot path over proto field names that may enter a `oneof` but not cross a `repeated` or `map` field) and either a fixed `type` or a `type_field` with an allow-list in `types`. `createProtoAuthzInterceptor` gains `resourceAuthorizer` (an object with `check({ subject, action, resource, context })` that returns `"allow"` or `"deny"`; no engine adapters ship), `hideExistence` (`{ action, byType? }`: a refused caller who also fails the visibility check gets `NotFound` instead of `PermissionDenied`), `services` (resolves every method at creation so a mistyped field path fails at startup) and `logger`. The resource check is an additional gate that runs after every allowing outcome of the method-level decision; it never overrides a denial by roles, scopes, `policy`, a rule or `authorize`, and a method that declares only `resources` is no longer denied by `defaultPolicy: "deny"` before the check. Only the literal `"allow"` allows, a thrown `ConnectError` keeps its code, any other exception becomes `Internal` without its text, a missing or empty id and a type outside `types` answer `InvalidArgument`, and a method with resource rules served without a `resourceAuthorizer` is denied. Rules are accepted on unary and server-streaming methods only (a server-streaming request is read once and handed to the handler again) and not on `public` methods. `ResolvedMethodAuth` gains an optional `resources`, and `ResourceRuleError` reports a rule that cannot be used. A server running `@connectum/auth` 1.3 ignores the new field and does not enforce it, so resource rules need 1.4 on the server.
