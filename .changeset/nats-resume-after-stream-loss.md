fix: a NATS subscription resumes after its JetStream stream was deleted and created again. Deleting a stream deletes its consumers; the client kept asking for a consumer that no longer existed, so `publish()` worked again after the stream was back while the handler never ran again, and nothing was logged. The adapter now logs the loss (`[EventBus/NATS] The server lost consumer ...`), polls for the stream (the pause grows to 5 seconds), creates the consumer again from the first message of the new stream (every message in it was published after the loss), replaces the client's message stream, and logs that delivery resumes; `unsubscribe()` and `disconnect()` stop the wait. A consumer that was deleted on its own while its stream still exists is not created again, as before, but the deletion is now logged once instead of passing silently. The adapter still does not create a deleted stream, and it gives up, with a log line, when the client has closed the connection for good. With overlapping patterns in one subscription, an event can run the handler twice while the consumers of the patterns are being recreated, and is never skipped.
