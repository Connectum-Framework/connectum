fix: `createAuthInterceptor` and `createSessionAuthInterceptor` now check the value returned by `verifyCredentials` and `mapSession`. A result that is not an `AuthContext` (`null`, `undefined`, `false`, `{}`, a string, or an object whose `subject`, `type`, `roles`, `scopes` or `claims` is missing or has the wrong type (`roles` and `scopes` must be arrays of at most 8192 strings and without holes; a sparse list, or a list that holds `undefined`, `null` or a number, is refused, so is a list of `String` objects or a proxy that reports a length that is not a non-negative safe integer within the limit, and so is an object whose property read throws), or whose `name` or `expiresAt` is mistyped) ends the call with `Unauthenticated` (`Authentication failed` / `Session mapping failed`) and is not cached, with `propagateHeaders` on or off. Before, such a result made the call fail with `internal` when `propagateHeaders` was on, and let the handler run without an identity when it was off. The steps that follow the check are held to the same outcome: if copying the identity for the cache or writing it into headers fails (a context property or a `claims` key whose getter throws, a proxy whose trap throws, a cyclic or `BigInt` claim, a value whose `toJSON` throws), the call ends with `Unauthenticated` instead of the raw error, and nothing is cached. The internal-auth interceptor treats a custom trust source result that is not an `AuthContext` like `null`. A callback that returned a partial object and relied on it being accepted must now return the complete `AuthContext`.
